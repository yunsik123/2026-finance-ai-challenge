# 먹투 (Meoktu)

좋아하는 식당을 실제 고객이 직접 펀딩하고, 혜택을 식당 할인 쿠폰으로 돌려받는 로컬 푸드 펀딩 MVP입니다.

## 바로 실행

```powershell
npm install
npm run dev
```

- 웹: `http://localhost:5173`
- 같은 와이파이의 다른 컴퓨터: 실행 PC의 내부 IP를 확인한 뒤 `http://<내부-IP>:5173`
- 투자자 심사용 로그인 계정: `investor@meoktu.demo` / `demo1234!`
- 소상공인 심사용 로그인 계정: `owner@meoktu.demo` / `demo1234!`
- 관리자 심사용 로그인 계정: `admin@meoktu.demo` / `demo1234!`
- 로그인 창 하단의 **투자자로 체험하기 / 사장님으로 체험하기**는 누를 때마다 초기화되는 별도 체험 세션입니다. 실제 기능을 그대로 눌러볼 수 있으며 투자자 체험은 시작 쿠폰 5장을 받습니다.

서버는 `0.0.0.0`에서 열리고, 모든 계정·주문·쿠폰은 `data/db.json`에 저장됩니다. Socket.IO로 거래 변경을 접속 중인 모든 브라우저에 알립니다.

## 구현된 핵심 흐름

- 투자자/소상공인 분리 회원가입과 로그인
- 로그인 시 투자자·사장님 유형을 먼저 선택하고, 원클릭 데모는 별도 세션으로 유지
- 역할별 메뉴: 공통 식당 발견·거래장·AI 인사이트·신고·문의, 투자자는 마이페이지, 사장님은 사장님 센터, 관리자는 전용 운영센터
- 가상 식당 12곳과 개별 펀드 12개
- 모금 중 즉시 투자·회수 및 모금 종료 후 1,000원 단위 FIFO 예약 매칭
- 목표액 1% 개인 투자 한도, 최초 투자자 가속 혜택
- 투자액·매출 보너스 기반 쿠폰 할인율 누적과 10% 이상 수동 발급
- 쿠폰 교환장: 조건부 등록 · 교환 제안 · 에스크로 · 수락/거절 · 거래 이력 (아래 참고)
- 쿠폰 사용 코드 발급과 사장님 매장 확인(실제 사용 혜택 집계)
- 6단계 소상공인 심사와 승인/조건부 승인/수동 검토/보완 결과 설명
- AI 데이터 상담원(역할별 원장 분리: 투자자는 지갑·예약, 사장님은 가게 모금·쿠폰 부담), 추천 식당 최대 3곳 비교, 상권·쿠폰 리포트
- 마이페이지 쿠폰 지갑: 상태별 필터(전체·사용 가능·교환 중·확인 대기), 사용 코드 발급, 지난 쿠폰 내역
- 펀드 예약 거래: 전체 투자/회수 대기 요약, 3단계 진행 안내, 내 순번과 앞 대기 금액 표시
- 식당별 5요소 투명 위험평가와 역할별 심사 절차 지식그래프
- 계정별 관심 식당, 이미지 증빙 AI OCR, 서버 감사 이력
- 주소 기반 상권분석 (유동인구·경쟁밀도·폐업률·임대료)과 위험모형 연동
- 사업자 진위확인(검증번호 포함)과 재무자료 AI 교차검증 6단계
- 사장님 쿠폰 발행·사용 손익 모니터링용 데이터 모델과 식당 감사 쿠폰 API
- 소상공인 직접 업로드와 제휴기관·마이데이터형 연결의 출처 분리
- 다운로드 가능한 PNG·PDF·CSV 심사 샘플과 CSV 열·행 검증
- 35개 지표 · 6개 업종 먹투 성장성 예비평가 엔진과 평가 근거·미산정 지표 공개
- 소상공인 지원제도 지식베이스와 실시간 심사현황 안내
- 펀드 예약 거래장(투자 대기 / 회수 대기 대기열)과 내 주문 취소
- 1:1 고객지원 문의 접수와 답변 확인
- 관리자 통합 운영센터: 회원·식당·펀드·심사·리뷰·문의·쿠폰 상태 관리와 AI 운영 점검
- 사장님 AI 경영 리포트와 기존 제출·다운로드 순서를 유지한 추가 펀딩 준비 화면
- 쿠폰 교환장 오른쪽 위의 주황색 “내 쿠폰 등록” 바로가기
- 체험 세션 전용 메모리 원장 — 실제 기능을 눌러보되 공유 원장은 바뀌지 않음

## 실제 로그인과 원클릭 체험의 차이

체험 모드는 이제 "막는 모드"가 아니라 **자기만의 임시 원장을 갖는 모드**입니다.
투자·쿠폰 발급·교환·리뷰·기관 연결·심사 접수까지 실제와 같은 버튼을 누르고 같은 결과를 보지만,
그 기록은 `server/demo.ts`의 메모리 샌드박스에만 남고 공유 원장(`data/db.json` 또는 Supabase `app_state`)은 전혀 바뀌지 않습니다.

| 구분 | 인증·저장 | AI 상담 | 자료 업로드·판독 | 투자·충전 | 쿠폰 발급·교환 | 리뷰 | 기관연결·심사 접수 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 이메일 로그인/회원가입 | Supabase Auth + 공유 Postgres 원장 | 가능 | 가능, 결과 저장 | 가능 | 투자자 최초 가입 시 쿠폰 5장 | 가능 | 가능 |
| 원클릭 투자자 체험 | 클릭할 때마다 새 4시간 임시 토큰 · 메모리 원장 | 가능 | 해당 없음 | 가능(체험 30만원 지급) | 시작 쿠폰 5장·발급·교환 가능 | 가능(본인에게만 보임) | 해당 없음 |
| 원클릭 사장님 체험 | 4시간 임시 토큰 · 메모리 원장 | 가능 | 가능 | 해당 없음 | 쿠폰 확인 가능 | 해당 없음 | 가능 |

동작 방식은 이렇습니다.

- 체험 토큰은 세션마다 다른 `sub`를 갖고(`demo-<role>-<랜덤>`), 그 id로 샌드박스 하나가 열립니다.
- 투자자·사장님 체험 버튼을 다시 누르면 새 토큰과 빈 샌드박스를 발급하므로 이전 체험의 투자·쿠폰·연결·심사 기록을 이어 쓰지 않습니다.
- 실제 투자자 계정의 가입 축하 쿠폰 5장은 최초 프로필 생성 때만 지급하며 재로그인에는 추가 지급하지 않습니다.
- `/api` 의 모든 쓰기 요청은 체험 세션이면 `handleDemoMutation()`이 가로채 샌드박스에 기록합니다.
- `/api/me`, `/api/public`, `/api/owner` 는 체험 세션에만 그 샌드박스를 덧씌워 돌려줍니다.
- 심사 접수(`POST /api/applications`)만은 실제 채점 로직을 그대로 쓰기 위해 원래 핸들러로 넘긴 뒤, 저장 직전에 샌드박스로 분기합니다.
- 샌드박스는 4시간이 지나거나 서버가 재시작되면 사라지고, 세션끼리도 서로 보이지 않습니다.

`tests/demo-and-data.ts`가 이 불변조건을 검사합니다: 체험 리뷰·투자가 공개 데이터에 새어 나오지 않고, 다른 체험 세션에도 보이지 않아야 통과합니다.

고정 심사용 로그인 계정(`investor@meoktu.demo` / `owner@meoktu.demo`)은 체험 버튼과 달리 실제 계정 모드이므로 공유 원장에 기록됩니다.

## 심사 데이터 출처와 샘플 파일

사장님 센터의 심사 자료는 두 경로로 나뉩니다.

1. **제휴기관·마이데이터형 연결** — POS, 사업용 계좌, 카드·VAN, 배달, 세무, 부채 정보. 제공기관·동의 범위·연결 시각·최근 동기화 시각을 서버 원장에 기록합니다. MVP 버튼은 실제 기관 API가 아닌 시연 어댑터이며, 브라우저가 임의로 보낸 `connectedSources` 문자열은 제휴 자료로 인정하지 않습니다.
2. **소상공인 직접 업로드** — 사업자등록, 영업신고, 임대차, 고객 가명 집계, 직원 집계 및 기관 연결이 어려울 때의 대체 자료. 파일명·크기·형식과 CSV 열·행 수를 검증하며, 이미지 OCR을 직접 실행한 경우 구조화 결과만 저장합니다.

심사 결과에는 `sourceProvenance.ownerUploaded`와 `sourceProvenance.partnerConnected`가 별도로 남아 누가 어떤 경로로 제공했는지 확인할 수 있습니다.

다운로드 가능한 가상 샘플은 `public/samples/`에 있습니다.

- `/samples/meoktu-business-sample.png` · `.pdf` — 사업자등록 증빙
- `/samples/meoktu-license-sample.png` · `.pdf` — 영업신고 증빙
- `/samples/meoktu-tax-sample.png` · `.pdf` — 부가가치세 과세표준 증빙
- `/samples/meoktu-lease-sample.png` · `.pdf` — 임대차 조건
- `/samples/meoktu-pos-sample.csv` — POS 주문·결제·취소
- `/samples/meoktu-account-sample.csv` — 사업용 계좌 입출금
- `/samples/meoktu-card-settlement-sample.csv` — 카드 승인·취소·정산
- `/samples/meoktu-sample-pack.zip` — 위 전체 묶음

모든 문서에는 “MVP SAMPLE · 실제 제출 불가” 배너와 워터마크가 들어 있습니다.
모든 값은 가상이며 실제 영업·세무·금융 증빙으로 사용할 수 없습니다.

### 샘플 재생성

```bash
node scripts/make-sample-data.mjs   # CSV 표 자료 8종
node scripts/make-sample-docs.mjs   # 문서 4종의 PNG·PDF와 묶음 zip
```

`make-sample-docs.mjs`는 `scripts/sample-docs/*.html`을 크롬 헤드리스로 렌더해 PNG와 PDF를 한 번에 만들고 zip까지 갱신합니다.
승재 프로젝트의 ReportLab 기반 서류 생성기(`generate_*_demo_docs.py`)와 같은 역할이며, 파이썬 런타임 없이 돌아가도록 옮긴 것입니다.
크롬 경로가 자동 탐지되지 않으면 `CHROME_PATH` 환경변수로 지정하세요.

## 공유 원장 (여러 인스턴스에서 같이 쓰기)

로컬은 `data/db.json` 을 그대로 씁니다. 그런데 Vercel 같은 서버리스는 요청마다 다른 인스턴스가 뜰 수 있고, 인스턴스마다 `/tmp` 가 따로라 파일 원장으로는 여러 사람이 같은 서비스를 쓸 수 없습니다. 같은 사용자가 새로고침 한 번에 잔액이 달라지고, 쿠폰이 복제되거나 사라집니다.

그래서 `STATE_STORE=supabase` 이면 원장을 Supabase Postgres 의 `app_state` 한 행에 두고 이렇게 동작합니다.

| 요청 | 동작 |
| --- | --- |
| 조회(GET) | 버전 번호만 먼저 확인하고, 바뀌었을 때만 원장을 다시 읽습니다. |
| 변경(POST/PATCH/DELETE) | `app_state` 행 잠금을 compare-and-set 으로 잡고, **잠금 안에서 최신 상태를 다시 읽은 뒤** 핸들러를 실행합니다. |

잠금은 15초 넘게 방치되면 자동으로 회수되므로 인스턴스가 죽어도 서비스가 멈추지 않습니다.

```bash
# 최초 1회: 공유 원장 테이블 생성 (SUPABASE_ACCESS_TOKEN 필요)
node scripts/apply-supabase.mjs

# 운영 스키마 초안까지 함께 적용하려면
node scripts/apply-supabase.mjs --full
```

Vercel 에서는 `SUPABASE_URL`(또는 `VITE_SUPABASE_URL`)과 `SUPABASE_SERVICE_ROLE_KEY` 가 있으면 자동으로 공유 원장을 씁니다. `STATE_STORE=file` 로 강제로 파일 원장을 쓸 수도 있습니다. `GET /api/health` 의 `stateStore` 값으로 현재 모드를 확인하세요.

## 상권분석 연동

`data/commercial-areas.json` 에 성수·연남·서촌·수원 행궁동·부산 전포·대전 은행동 6개 상권의 공개 지표를 담았고, `server/commercial.ts` 가 식당 주소로 상권을 찾습니다.

- **exact** — 동 이름이 상권 별칭과 일치 (예: 목화다방 성수동 → 성수동 상권)
- **nearby** — 동 데이터는 없지만 같은 시·구 (예: 바다의 식탁 부산 광안리 → 부산 전포 상권을 참고값으로)
- **미연동** — 짐작으로 붙이지 않습니다. 화면에 "상권 원천데이터 미연동"으로 표시하고, 위험평가의 데이터 신뢰도를 낮춰 보여줍니다.

연결된 상권 지표는 세 곳에서 쓰입니다.

1. 위험평가의 **상권 회복력** 구성요소 — 식당 자체 추정치 대신 유동인구 성장·상권 매출 성장·폐업률·경쟁밀도·임대료 상승으로 계산합니다.
2. **역할별 지식그래프**의 `CommercialArea` 노드 — AI 상담원이 상권을 근거로 인용합니다.
3. 식당 상세 모달의 **입지 분석 카드**.

점수에 직접 넣기 애매한 신호(경쟁 밀집, 높은 폐업률, 임대료 급등, 외지 소비 편중)는 점수를 흔들지 않고 **맥락 경고**로 따로 보여줍니다.

## 사업자 진위확인과 재무 교차검증

`server/verification.ts` 가 두 가지를 담당합니다.

**사업자 진위확인** — 사업자등록번호 10자리 형식과 **국세청 검증번호 규칙**, 대표자명, 영업신고번호, 대표자 본인인증을 확인합니다. 형식·검증번호 오류는 접수 단계에서 바로 돌려보내 오타를 잡아줍니다. 실제 국세청 API를 붙일 때는 `verifyBusiness` 어댑터 구현만 교체하면 됩니다.

**재무자료 AI 교차검증 6단계** — 사장님이 올린 이미지의 AI OCR 판독 결과를 신고 수치와 대조합니다.

| 단계 | 확인 |
| --- | --- |
| 사업자 식별값 대조 | 문서에서 읽은 사업자번호 ↔ 신고한 번호 |
| 문서 기준기간 확인 | 판독 문서에 기준일자가 있는지 |
| 매출 교차검증 | POS·카드 문서 판독액 ↔ 산출 매출 |
| 부채·상환액 교차검증 | 부채 증빙 판독액 ↔ 신고 상환액 |
| 납세 상태 교차검증 | 납세 자료 판독 판정 |
| 문서 간 모순·중복 검사 | 같은 내용 문서 중복 제출 여부 |

전에는 OCR 결과가 저장만 되고 심사에 쓰이지 않았습니다. 지금은 **불일치가 발견되면 점수와 무관하게 수동 심사로 넘어갑니다.** AI 판독은 어디까지나 보조자료이고, 통과로 표시돼도 운영자가 원본을 확인해야 공식 재무심사가 됩니다.

## 35개 지표 · 6개 업종 먹투 성장성 예비평가 (`server/credit.ts`)

`/api/applications` 심사가 끝나면 5요소 상권 위험평가와 **별개로** 35개 지표 먹투 성장성 예비평가가 함께 계산됩니다.
둘은 보는 대상이 달라 평균을 내지 않고 나란히 보여주며, 화면용 종합값만 `combineAssessments()`로 섞습니다
(성장성·상권 40% + 신용·현금흐름 60%).

신청서의 먹투 성장성 예비평가 점수와 AI 제안 한도는 이 35개 지표 가중점수를 기준으로 합니다. A·A+(75점 이상)는 승인 제안,
B·B+(55점 이상)는 조건부 승인 권고, C(45점 이상)는 수동 검토, D는 보완 대상으로 분류합니다.
다만 산정률 50% 미만, 핵심 매출·현금흐름 미산정, 사업자 검증 실패 또는 자료 불일치가 있으면 점수와 무관하게 수동 검토로 전환합니다.

| 그룹 | 가중치 | 지표 수 | 대표 지표 |
| --- | --- | --- | --- |
| 신용·부채 | 25% | 4 | 연체 횟수, 최대 연체일수, 총 대출잔액, 거래 금융기관 수 |
| 매출·거래 | 24% | 8 | 12개월 평균 카드매출, 3·12개월 성장률, 상대 성장률, 매출 변동성, 환불비율 |
| 현금흐름 | 27% | 4 | 평균·최저 현금잔액, 순현금흐름 비율, 원리금상환/현금유입 |
| 운영·상권 | 14% | 7 | 업력, 직원 증가율, 상권 매출·유동인구 성장, 경쟁 밀도, 폐업률, 상대순위 |
| 고객·평판 | 10% | 12 | 재방문율, 고객 증가율, 평점 평균·분산, 부정 리뷰 비율, 측면별 감성 |

- **6개 업종**: 외식 / 도소매 / 숙박 / 제조 / 부동산 / 보건. 업종마다 매출·객단가 기준선과 참고 폐업률이 다릅니다.
- **점수화**: 업종 기준분포의 하위10%·중앙·상위10% 세 점을 지나는 꺾은선으로 백분위를 근사하고, 낮을수록 좋은 지표는 뒤집습니다.
- **등급**: A+ 85 / A 75 / B+ 65 / B 55 / C 45 / D.
- **정책 오버라이드**: 최대 연체일수 90일 이상이면 점수와 무관하게 D. 측정 가중치가 50% 미만이면 70점 상한으로 상위 등급을 보류합니다.
- **미산정 처리**: 자료가 없는 지표는 0점으로 깎지 않고 가중치에서 빼고 나머지로 재정규화합니다. 대신 `coverage`(지표 산정률)가 떨어져 신뢰도로 드러납니다.

지표 목록·가중치·등급 경계는 승재 프로젝트의 신용평가 시뮬레이터(`validate_credit_model.py`, 5,000개 합성표본 검증)에서 그대로 가져왔고,
변수 설계와 운영 원칙은 페루 미소금융 논문 두 편을 따랐습니다.

| 연구 | 적용한 것 | 하지 않은 것 |
| --- | --- | --- |
| Blanco et al. (2013) 페루 미소금융 신용평가 | 재무비율만이 아니라 대출조건·연체·거시변수를 나눠 저장하는 변수 설계 | 논문의 MLP·AUC·부도확률 재현 (동일 정의의 부도 라벨이 없음) |

관련 API:

- `GET /api/credit/model` — 지표 목록·가중치·업종 프로필·등급 경계·참고 연구를 반환하는 운영·검증용 API입니다(특정 사업체 값 없음).
- `POST /api/ai/management-credit-diagnosis` — 사장님 전용 경영·신용 진단. 강점/위험/할 일과 등급 근거를 함께 냅니다. (승재 프로젝트의 같은 이름 엔드포인트를 먹투 모델로 옮긴 것)

**이 결과는 먹투 성장성 예비평가입니다.** 금융기관의 공식 신용평가나 정부 SCB 결과가 아니고 부도확률을 계산하지 않으며, 자동으로 거절하지 않습니다.

## 소상공인 지식베이스와 실시간 심사현황 (`server/knowledge.ts`)

AI 상담원이 두 종류의 정보를 같은 자리에서 씁니다.

1. **공적 지원제도 10종** — 정책자금, 지역신용보증재단 보증, 노란우산공제, 부가세 간이과세·세액공제, 두루누리 사회보험, 희망리턴패키지, 역량강화 교육·컨설팅, 온라인 판로·스마트상점, 상권정보시스템, 카드수수료 우대.
   제도별로 대상·혜택·신청 창구·유의사항을 담고, 금액·금리·기간은 해마다 바뀌므로 기준월(`knowledgeAsOf`)과 "기관 공고를 확인하세요"를 항상 함께 냅니다. 먹투가 대신 신청해주는 것처럼 말하지 않습니다.
2. **사장님 현재 상황** — 요청 시점마다 `ownerSituation()`이 계산합니다. 6단계 중 몇 번째인지, 확보한 자료와 아직 없는 필수 자료, 대조에서 어긋난 값의 수, 다음에 하면 좋은 일 최대 4가지.

덕분에 "내 심사 지금 어떻게 돼가?", "뭐가 부족해?", "정책자금 받을 수 있어?" 같은 질문에 절차 설명이 아니라 실제 값으로 답합니다.

## 펀드 예약 거래장 (호가창)

모금이 끝난 펀드는 가격이 움직이지 않습니다. 1,000원은 언제나 1,000원이고 **누가 먼저 줄을 섰는지**만 남습니다.
그래서 승재 프로젝트의 가격·시간 우선 호가창 대신 **시간 우선 단일가 대기열**로 옮겨 붙였습니다.

주문 자체는 예전부터 `db.orders`에 쌓이고 `matchOrders()`가 FIFO로 체결해 왔는데 화면에서 볼 방법이 없었습니다.
`GET /api/market/orderbook`이 그 창이고, 거래장 위쪽 **펀드 예약 거래** 탭에서 식당별 투자 대기 / 회수 대기 줄과 내 순번을 봅니다.
대기열은 익명이라 누가 얼마를 걸었는지가 아니라 **내 앞에 얼마가 있는지**만 보여주고, 내 주문에만 취소 버튼이 붙습니다.

## 1:1 고객지원

AI 상담원은 공개된 정보와 절차만 답할 수 있습니다. 내 계정의 거래나 심사처럼 사람이 확인해야 하는 문제를 넘길 창구가 없어
사용자가 막다른 길에 놓였었습니다. 승재 프로젝트의 문의 접수(`disputes`)를 먹투 모델로 옮겨 `/support` 화면과
`GET·POST /api/support/requests`를 추가했습니다. 투자·회수와 계정 문의는 자동으로 높은 우선순위가 붙고, 접수 즉시 알림이 갑니다.
AI 시스템 프롬프트도 "고객센터가 없다"에서 "1:1 문의 화면으로 안내한다"로 바뀌었습니다.

## 쿠폰 교환장 (여러 사람이 동시에 쓰는 것을 전제로 설계)

쿠폰 교환은 서버가 판정하고 서버가 체결합니다. 화면은 안내만 하고, 최종 검증은 항상 체결 직전에 다시 실행됩니다.

**교환이 성립하는 조건** (`server/exchange.ts` 한 곳에만 정의되어 있고 `/api/market/rules`로 공개됩니다)

| 규칙 | 값 | 이유 |
| --- | --- | --- |
| 할인율 차이 | 10%p 미만 | 한쪽이 크게 손해 보는 교환 방지 |
| 최대 할인 금액 차이 | 2.5배 이내 | 같은 30%라도 2,880원과 11,520원은 값어치가 다름 |
| 만료 여유 | 7일 이상 | 곧 죽는 쿠폰 떠넘기기 방지 |
| 등록자 조건 | 업종·지역·최소 할인율 | 등록자가 지정한 조건을 서버가 강제 |

**흐름**

1. **등록** — 지갑에서 쿠폰을 올릴 때 원하는 업종·지역·최소 할인율·교환 방식(즉시/승인)을 직접 고릅니다. 올린 쿠폰은 잠깁니다.
2. **제안** — 교환장에서 *내가 어떤 쿠폰을 내줄지 직접 고릅니다.* 제안한 쿠폰은 결과가 날 때까지 잠겨(에스크로) 여러 곳에 중복으로 걸 수 없습니다.
3. **체결** — 즉시 교환 매물은 바로, 승인형은 등록자가 수락할 때 체결됩니다. 체결 시 같은 매물의 다른 제안은 자동 반려되고 걸려 있던 쿠폰이 모두 풀립니다.
4. **기록** — 모든 체결은 `couponTrades` 원장과 감사 이력에 남고, 양쪽에 알림이 갑니다.
5. **사용** — 지갑에서 **사용하기**를 누르면 8자리 코드가 발급되고, 사장님이 사장님 센터에서 코드를 확인하면 실제 사용 처리되며 펀드의 누적 사용 혜택에 반영됩니다. 20분 안에 확인되지 않으면 지갑으로 되돌아옵니다.

**동시성** — 교환 관련 쓰기는 전부 하나의 큐로 직렬화되고(`withExchangeLock`), 잠금 안에서 조건을 다시 검사합니다. 두 사람이 같은 매물을 동시에 집어가면 정확히 한 명만 성공합니다 (`tests/coupon-exchange.ts`에서 검증).

**자동 정리** — 만료된 쿠폰·등록(30일)·제안(7일)은 조회·쓰기 직전마다 정리되어 유령 매물이 남지 않습니다.

**남용 방지** — 등록·제안·교환·사용확인·AI 호출에 계정(또는 IP) 단위 슬라이딩 윈도 제한이 걸려 있습니다.

## AI 연결

현재 서버는 **Google Vertex AI (Gemini)** 로 생성형 답변과 영수증·증빙 OCR을 처리합니다.
Vertex 의 OpenAI 호환 엔드포인트를 쓰기 때문에 요청 형식은 Chat Completions 그대로이고,
JSON 응답 강제(`response_format`)와 이미지 입력(`image_url`)도 동일하게 동작합니다.

**API 키가 없습니다.** Vertex 는 수명 1시간짜리 OAuth 토큰을 쓰며, `server/ai-provider.ts` 가
아래 순서로 자격증명을 자동으로 찾아 토큰을 갱신합니다.

1. **메타데이터 서버** — Cloud Run·GCE 안에서 서비스 계정이 자동으로 붙습니다. 배포본에는 키 파일이 아예 없습니다.
2. `GOOGLE_APPLICATION_CREDENTIALS` — 서비스 계정 키 파일(JWT 서명 후 교환)
3. **로컬 ADC** — `gcloud auth application-default login` 으로 만든 사용자 자격증명

로컬 준비는 이 한 줄이면 됩니다.

```bash
gcloud auth application-default login
```

환경변수(전부 선택, 기본값으로 동작):

- `GOOGLE_CLOUD_PROJECT`: GCP 프로젝트 ID (없으면 자격증명에서 자동 추론)
- `VERTEX_LOCATION`: 기본값 `global` — **리전 엔드포인트는 모델에 따라 404가 납니다. 바꾸지 마세요.**
- `VERTEX_CHAT_MODEL`: 상담 모델 (기본값 `gemini-3-flash-preview`)
- `VERTEX_OCR_MODEL`: 증빙 판독 모델 (기본값 `gemini-3-flash-preview`)
- `VERTEX_THINKING_BUDGET`: 생각 토큰 상한 (기본값 `512`)

> **생각 토큰 주의**: Gemini 3 는 답을 쓰기 전 "생각"에 토큰을 쓰고 그 토큰도 `max_tokens`
> 예산에서 나갑니다. 상한을 걸지 않으면 생각만 하다 본문이 잘려 JSON 파싱이 실패합니다
> (실제로 1,400 예산 중 2,495를 생각에 써서 리포트가 끊겼습니다). `server/ai-provider.ts` 의
> `aiJsonExtras()` 가 `thinking_budget` 하드 캡을, `aiTokenBudget()` 이 예산 여유를 함께 겁니다.

`GET /api/health` 의 `aiProvider`·`aiCredential`·`aiModel` 로 현재 연결 상태를 확인할 수 있습니다.

이미지 OCR은 사장님이 문서별 **AI 문서 판독**을 직접 누른 경우에만 서버를 통해 호출됩니다. 원본 이미지는 로컬 JSON DB에 저장하지 않고 구조화된 판독 결과와 감사 이력만 남깁니다. AI 설정이 없거나 호출에 실패하면 자동 승인하지 않고 `manual_review`로 기록합니다.

## 데이터 저장과 운영 전환

로컬 실행은 설치 없이 확인하기 쉬운 `data/db.json` 원장을 계속 사용합니다. `db/postgres-schema.sql`에는 소상공인 프로젝트와 승재 프로젝트의 DB 설계를 합쳐 PostgreSQL/Supabase 전환용 테이블, 인덱스와 RLS 정책을 마련했습니다. 운영에서는 투자·회수·FIFO 매칭과 운영자 승인을 브라우저 직접 쓰기가 아닌 트랜잭션 RPC로 구현하고, `SUPABASE_SERVICE_ROLE_KEY`는 서버 환경변수에서만 사용해야 합니다.

## Supabase Auth

서버에 `SUPABASE_URL`(또는 `VITE_SUPABASE_URL`)과 `SUPABASE_PUBLISHABLE_KEY`(또는 `VITE_SUPABASE_PUBLISHABLE_KEY`)가 있으면 일반 회원가입·로그인은 Supabase Auth를 우선 사용합니다. `SUPABASE_SERVICE_ROLE_KEY`까지 서버에 설정하면 회원가입 시 이메일 확인을 완료한 사용자를 서버에서 만들고 즉시 로그인합니다. 서비스 역할 키는 절대로 `VITE_` 접두어로 노출하지 않습니다.

Supabase가 설정되지 않은 로컬 환경과 `@meoktu.demo` 심사용 고정 계정은 기존 로컬 인증으로 계속 동작합니다. 로그인 창 하단의 원클릭 체험은 이 고정 계정에 로그인하지 않고 별도 임시 토큰을 사용합니다. `GET /api/health`의 `authProvider` 값으로 현재 인증 모드를 확인할 수 있습니다.

`SUPABASE_AUTH_DISABLED=1`을 주면 Supabase 키가 있어도 로컬 데모 인증만 사용합니다. 통합 테스트는 항상 이 모드로 서버를 띄우므로, 테스트를 돌려도 실제 Supabase 프로젝트에 계정이 생기지 않습니다.

### AI 상담 성능 평가 (`npm run test:ai`)

통합 테스트와 별개로, 상담원 품질을 30문항으로 채점하는 하네스가 있습니다. **실제 외부 AI를 호출하므로 API 비용이 발생합니다.** 그래서 `test:integration` 에는 포함하지 않았습니다.

```bash
# 서버를 먼저 띄운 뒤
MEOKTU_TEST_PORT=8801 npm run test:ai
```

문항은 세 묶음입니다.

| 묶음 | 문항 | 채점 기준 |
| --- | --- | --- |
| A. 비로그인 (10) | 투자 시작·쿠폰 교환·예약 취소·충전·문의·식당 설명·회수·쿠폰 조건·리뷰·최초 투자자 혜택 | 실제 화면 메뉴/버튼 이름으로 안내하는지 |
| B. 투자자 (10) | 잔액·쿠폰 수·예약 주문·현재 화면·관심 식당·알림·쿠폰 사용법·교환 등록법·성장성 예비평가·공개정보 비교 | 답변 숫자가 그 시점 DB 원장과 **정확히 일치**하는지, 사장님 비공개 근거가 안 붙는지 |
| C. 사장님 (10) | 심사 단계·모금 현황·투자자 수·쿠폰 부담·부족 자료·추가 펀딩·경영 리포트·식당 감사 쿠폰·매출 공개·정책자금 | 가게 운영 원장으로 답하는지, 투자자용 지갑 값이 섞이지 않는지 |

모든 문항에 공통으로 **내부 용어 미노출**(GraphRAG·지식그래프·노드·LLM·OCR·프롬프트·임베딩·벡터·토큰)과 빈 답변 여부를 함께 검사합니다.

> 테스트는 빈 원장의 임시 복사본에서 실행하는 것을 권장합니다. 실제 운영 Supabase Auth를 건드리지 않도록 `SUPABASE_AUTH_DISABLED=1`이 강제됩니다.

개발 서버가 이미 8787을 쓰고 있으면 다른 포트와 별도 원장으로 돌릴 수 있습니다. 그러면 개발 중 쓰던 쿠폰 매물이 테스트로 소진되지 않습니다.

```bash
MEOKTU_DATA_DIR=.tmp/test-ledger MEOKTU_TEST_PORT=8799 npm run test:integration
```

- `MEOKTU_DATA_DIR` — 서버가 쓸 원장 디렉터리 (기본 `data/`)
- `MEOKTU_TEST_PORT` / `MEOKTU_TEST_BASE` — 테스트가 붙을 주소 (기본 `http://localhost:8787`)


```bash
npm run test:integration
```

`tests/run.ts`가 `SUPABASE_AUTH_DISABLED=1`로 서버를 직접 띄우고 9개 스위트를 실행한 뒤 서버를 정리합니다. 8787에 이미 서버가 떠 있으면 그 서버를 재사용하되, Supabase Auth 모드라면 실제 프로젝트를 오염시키지 않도록 실행을 중단합니다. 관리자 스위트는 권한 차단과 통합 대시보드, 회원·식당·리뷰 운영 액션을 변경 후 원래 값으로 복구하며 검증합니다. AI·화면 스위트는 상담 답변이 실제 DB 원장 값과 같은지, 역할별 원장이 섞이지 않는지, 화면 버튼이 부르는 API가 실제로 도는지를 확인합니다.

`npm run build`와 `npm run check`는 `tsc -b --force`를 사용합니다. 증분 캐시(`.tsbuildinfo`)가 남아 있으면 실제 구문 오류를 건너뛰고 통과할 수 있어, 배포에서만 빌드가 깨지는 사고를 막기 위한 조치입니다.

## AI 상담원

모든 페이지 오른쪽 아래의 **AI와 상담하기** 버튼과 `AI 인사이트` 화면의 상담창은 같은 엔드포인트(`POST /api/ai/chat`)를 씁니다.

답변 근거는 다섯 갈래로 모입니다.

1. **화면 지도** (`server/sitemap.ts`) — "어디서 하나요" 류 질문에 실제 메뉴명·버튼명·클릭 순서로 답합니다. 브라우저가 함께 보내는 `currentPath`로 "지금 이 화면"이 무엇인지도 압니다.
2. **역할별 심사 절차** (`server/trust.ts`) — 투자자/소상공인 각각의 확인 순서와 지금 보고 있는 식당·펀드·평가 정보.
3. **소상공인 지원제도** (`server/knowledge.ts`) — 정책자금·보증·세제·공제·재기지원 등 먹투 밖의 공적 제도.
4. **사장님 현재 상황** (`server/knowledge.ts`의 `ownerSituation()`) — 요청 시점에 계산하는 심사 단계, 확보·누락 자료, 불일치 건수, 다음에 할 일.
5. **내 계정 원장** (`server/index.ts`의 `consultationAccount()` / `ownerLedgerFor()`) — 로그인한 사람의 현재 값.

### 역할에 따라 원장이 완전히 갈립니다

같은 "내 현황 알려줘"라도 투자자와 사장님은 봐야 할 숫자가 다릅니다. 역할은 요청 본문이 아니라 **로그인 토큰**에서 다시 확인합니다.

| | 투자자 (`account-ledger-local`) | 사장님 (`owner-ledger-local`) |
| --- | --- | --- |
| 원장 | 먹투머니 잔액, 투자 중인 식당 수·금액, 보유 쿠폰 상태별 장수, 예약 주문 대기 금액, 교환 제안, 알림, 관심 식당 | 내 가게의 회차·모금 목표·모금액·투자자 수, 발급/사용된 쿠폰 금액, **아직 사용되지 않은 쿠폰 부담**, 확인 대기 쿠폰, 매출 공개 여부, 심사 결과, 내 문의 |
| 우선순위 | 내 원장 → 지금 화면 → 화면 위치 → 지원제도 → 절차 | 심사 질문이면 심사 현황 우선, 모금·쿠폰·투자자 같은 운영 수치면 운영 원장 우선 |

- 개인 원장 값은 **외부 생성형 서비스로 보내지 않습니다.** 서버가 원장에서 직접 집계한 답을 그대로 돌려주고, `provider`는 `meoktu-private-ledger`가 됩니다.
- 투자자가 요청 본문에 `role: 'owner'`를 넣어도 사장님의 심사·신용·제출자료 노드는 붙지 않습니다. 심사 근거는 그 가게의 **소유자 본인** 상담에만 실립니다.

질문 유형에 따라 우선순위가 갈립니다. "내 심사 어디까지 됐어?"는 절차 설명이 아니라 ④의 실제 값으로,
"펀드 등록 어디서 해?"는 ①의 클릭 경로로 답합니다. AI 키가 없거나 외부 호출이 실패해도 같은 근거로 로컬 답변을 만듭니다.

### 사용자에게 내부 용어를 보여주지 않습니다

소상공인과 일반 투자자가 쓰는 화면이므로 GraphRAG, 지식그래프, 노드, OCR, LLM 같은 말은 화면과 답변 어디에도 나오지 않습니다.
시스템 프롬프트에 금지어 목록이 있고, 화면 문구도 "먹투에 공개된 식당 정보와 이용 절차를 확인해서 알려드려요"처럼 사람 말로 씁니다.
감사 로그의 동작 코드(`application.credit_graded` 등)도 사장님 화면에서는 한국어 라벨로 바뀝니다.

### 화면 문구를 바꾸면 sitemap.ts도 함께 고치세요

`server/sitemap.ts`의 메뉴명·버튼명은 실제 화면과 1:1로 맞춰야 합니다.
안 고치면 AI 상담원이 존재하지 않는 버튼을 안내하게 됩니다. 파일 맨 위 주석에도 같은 내용이 적혀 있습니다.

## Vercel

`api/index.ts`가 Express 서버리스 함수 진입점이고, `vercel.json`이 `/api/*` 요청을 함수로 전달하고 나머지 경로를 Vite SPA로 연결합니다. 필요한 Vercel 환경변수는 다음과 같습니다.

- `STATE_STORE=postgres`
- `INSTANCE_CONNECTION_NAME` (Cloud Run), 또는 `DATABASE_URL` (로컬·스키마 적용)
- `DB_USER`, `DB_PASSWORD`, `DB_NAME`
- `GOOGLE_CLOUD_PROJECT`, `VERTEX_LOCATION=global`
- `VERTEX_CHAT_MODEL`, `VERTEX_OCR_MODEL` (선택, 기본: `gemini-3-flash-preview`)
- `NEO4J_URI`, `NEO4J_USER`, `NEO4J_PASSWORD` (선택 — 없으면 서버 내장 그래프로 동작)
- `APP_SECRET`

암호는 전부 Secret Manager 에 두고 Cloud Run 이 `--set-secrets` 로 주입받습니다.
저장소에도 이미지에도 평문 암호가 남지 않습니다.

운영 Vercel은 `STATE_STORE=supabase`로 Supabase의 `app_state` 한 행을 공유 원장으로 사용합니다. `STATE_STORE=supabase`인데 URL 또는 service role 키가 없으면 파일 원장으로 조용히 후퇴하지 않고 시작 단계에서 오류를 냅니다. `db/postgres-schema.sql`의 정규화 테이블과 트랜잭션 RPC는 후속 확장용 설계이며, 현재 MVP의 운영 쓰기는 `app_state` compare-and-set 잠금으로 직렬화됩니다.

## 운영 한도와 확장 한계

실제 트래픽에서 무엇이 먼저 막히는지, 어디까지 견디는지를 실측한 값으로 적는다.

### 요청 한도 — 전부 환경변수로 조절한다

한도는 두 종류다. **도배 방지**(비용과 무관)와 **비용 방어**(생성형 호출 = Vertex AI 요금).
값이 코드에 박혀 있으면 서비스 중에 막혔을 때 재배포해야 하므로 전부 환경변수로 뺐다.

```bash
# 재배포 없이 즉시 반영된다
gcloud run services update meoktu --region=asia-northeast3 \
  --update-env-vars=LIMIT_AI_CHAT=500,LIMIT_OWNER_REPORT=1000
```

기본값은 `.env.example` 에 있다. `0` 이하를 주면 그 한도를 끈다.
다만 생성형 한도를 끄면 반복 호출이 그대로 요금이 되므로, 끄기보다 넉넉히 올리는 편을 권한다.

> 한도 카운터는 인스턴스 메모리에 있다. Cloud Run 인스턴스가 N 개로 늘어나면
> 실효 한도도 대략 N 배가 된다. 정확한 총량 제한이 필요하면 공유 저장소가 필요하다.

### 동시성 — 생성형 경로는 전역 잠금을 잡지 않는다

원장 쓰기는 전역 잠금으로 직렬화된다. 인스턴스가 여러 개로 늘어나도 쿠폰·투자 원장이
갈라지지 않게 하려는 설계다. 문제는 **POST 라는 이유만으로 AI 경로까지 그 잠금을 쥐고 있었다**는 것이다.
생성형 응답은 8~16초가 걸리므로, AI 상담 한 명이 그 시간 내내 서비스 전체의 쓰기를 멈춰세웠다.

실측(수정 전 → 수정 후, 동시 12건):

| | 성공 | 응답 형태 |
|---|---|---|
| 수정 전 | 1 / 12 | 8초 → 16초 → 18초로 직렬화, 나머지는 9초 대기 후 503 |
| 수정 후 | 12 / 12 | 7.8~12.8초 병렬 |

동시 30건도 30/30 성공(평균 8.0초). AI 10건이 처리되는 중에 쓰기 요청(로그인)은 0.15초에 끝난다.

`UNLOCKED_AI_PATHS` 에 있는 경로는 잠금을 건너뛰고, 원장에 남길 것이 있을 때만
`withWriteLock()` 으로 수십 ms 만 잠근다. 새 AI 경로를 추가하면 이 집합에도 넣어야 한다.

### DB 연결 수

`DB_POOL_MAX`(기본 5) × Cloud Run 최대 인스턴스(40) = 200. Cloud SQL `db-custom-2-7680` 의
`max_connections` 는 **400** 이라 절반만 쓴다. 예전 기본값 10 이면 정확히 400 이라 부하 시 고갈됐다.
인스턴스 수나 티어를 바꾸면 이 곱을 다시 계산해야 한다.

### 실시간 반영

소켓 브로드캐스트(`io.emit`)는 그 요청을 처리한 인스턴스에 붙은 브라우저에만 간다.
인스턴스가 여러 개면 다른 인스턴스의 변경은 소켓으로 오지 않는다.
그래서 브라우저는 소켓이 붙어 있어도 `/api/version` 을 10초마다 확인하고,
버전 숫자가 달라졌을 때만 전체 상태를 다시 받는다.
(`/api/version` 45바이트 vs `/api/public` 92KB — 폴링 비용은 사실상 없다.)

### 아직 남아 있는 확장 한계

**원장 전체를 읽고 쓰는 구조**가 가장 먼저 벽에 부딪힌다.
`meoktu.read_ledger()` 는 테이블 24개에서 원장 JSON 을 통째로 조립하고,
쓰기는 그 JSON 전체를 다시 저장한다. 게다가 쓰기는 전역 잠금으로 직렬화된다.

실측(사용자 17명): 응답 **77KB**, 조회 **186ms**.

사용자가 늘면 이 크기와 시간이 선형으로 늘고, 모든 쓰기가 그 시간만큼 줄을 선다.
수백 명 규모까지는 버티지만 그 이상에서는 **라우트를 개별 테이블 질의로 바꾸는 작업**이 필요하다.
스키마·트랜잭션 RPC(`db/functions.sql`)는 이미 그 구조로 만들어져 있으므로,
바꿔야 하는 것은 라우트가 원장 전체 대신 필요한 행만 읽도록 하는 부분이다.

**인스턴스 메모리에만 있는 상태**도 확장 시 주의가 필요하다.
체험 세션(`server/demo.ts`)은 인스턴스 메모리에 산다. 세션 어피니티로 대부분 같은 인스턴스에
붙지만, 인스턴스가 정리되면 체험 내용이 사라진다. 시연 중에는 `DEMO=1` 로 배포해
`min-instances=2` 를 유지하면 이 위험이 줄어든다. 생성형 분석 캐시도 인스턴스별이라
인스턴스가 늘면 같은 분석을 여러 번 호출할 수 있다(결과는 같고 요금만 는다).

## 실제 서비스 전 필요한 연동

- 사업자등록·영업신고·대표자 본인확인 제공사
- 여신금융협회/카드사 또는 POS 매출 데이터 제휴
- 국세·지방세 납부 및 행정처분 확인 가능한 합법적 데이터 제휴
- 상권 유동인구·업종 매출·폐업률 데이터(KOSIS, 소상공인시장진흥공단 등)
- 결제/예치금/정산 사업자와 전자금융·자본시장·유사수신 관련 법률 검토
- 공개 배포용 관리형 DB(PostgreSQL 등), 비밀번호 재설정과 이메일 인증

현재 코드는 기능 검증용 MVP입니다. 실제 투자금 수취나 보관 기능을 켜기 전에 금융·소비자보호·개인정보 법률 검토가 반드시 필요합니다.
