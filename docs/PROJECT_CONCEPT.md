# 모아(MOA) 프로젝트 컨셉 및 현재 구현 설계

> 지역 고객이 검증된 소상공인 사업계획에 참여하고, 투자 유지기간에 따라 해당 가게에서 쓸 수 있는 쿠폰 혜택을 받는 지역 상생형 펀딩 서비스

- 기준일: 2026-08-30
- 현재 구조: Vite 프론트엔드 + Supabase Auth/PostgreSQL/RLS/RPC + Vercel AI API
- 사용자: 투자자, 소상공인, 운영자
- 현재 상품: 현금 이자·지분·원금상환을 약속하는 증권형 상품이 아니라 소비 쿠폰형 참여 모델
- 주의: 공개 예시 6건은 가상 사업체다. 실제 투자 권유나 수익 보장이 아니다.

---

## 1. 한 줄 정의와 해결할 문제

모아는 소상공인이 사업계획과 근거자료를 제출하고, 투자자가 사업·재무·입지·위험·집행조건을 함께 검토한 뒤 참여하며, 운영자가 모집 전 검증과 모집 후 단계별 지급을 통제하는 서비스다.

### 소상공인

- 담보·신용 이력이 부족해도 실제 사업과 성장계획을 설명할 채널이 필요하다.
- 매출, 부채, 상권 자료가 흩어져 있고 이를 신뢰성 있게 입증하기 어렵다.
- 모집 이후에도 자금 사용과 진행상황을 반복적으로 설명해야 한다.

### 투자자

- 좋은 이야기뿐 아니라 매출 근거, 현금흐름, 부채, 입지, 경쟁, 폐업 위험을 함께 봐야 한다.
- 사업자가 직접 입력한 주장과 운영자가 확인한 사실을 구분해야 한다.
- 참여 후 중요 변경, 목표별 증빙, 자금 지급 상태를 계속 추적할 수 있어야 한다.

### 운영자

- 허위 사업체·조작 수치·중복 문서·계획과 무관한 집행을 순서대로 걸러야 한다.
- AI가 숫자를 추출하는 일과 사람이 승인하는 일을 분리해야 한다.
- 외부 결제·예치 제공자가 중단돼도 원장과 감사 기록을 보존할 수 있어야 한다.

## 2. 현재 상품과 법적 경계

현재 구현은 투자금 유지기간에 따라 음식점 쿠폰 할인율이 쌓이는 소비 쿠폰형 참여 모델이다. 현금 이자, 수익률, 지분, 원금상환을 약속하지 않는다. 화면의 “투자”라는 용어만으로 규제 성격이 결정되는 것은 아니므로 실제 결제 전에 선불전자지급수단, 전자상거래, 금융투자상품 또는 온라인소액투자중개 해당 여부를 국내 전문가와 확정해야 한다.

실제 금전 거래 전 필수 조건:

1. 상품 법률 검토와 약관·위험고지 버전 관리
2. 본인확인, 사업자 진위, KYC/AML 및 제재·부정행위 확인
3. 결제·예치·취소·최소 성립액 미달 환불
4. 중요 조건 변경 시 통지와 참여자 재확인
5. 장애·폐업·분쟁·환불·개인정보 보존 절차

## 4. 사용자 흐름

### 투자자

1. 투자자 계정으로 로그인하거나 공개 예시를 탐색한다.
2. 관심 위치·주소를 입력해 상권 수요, 성장, 경쟁, 폐업 위험과 주변 모집을 본다.
3. 모아 상품이 현금 이자·지분이 아닌 쿠폰형 참여임을 확인한다.
4. 사업자 확인, 공식 재무검증 배지, 자금계획, 위험, 상권, 지급단계를 검토한다.
5. 생활자금을 제외하고 사업체 집중도와 회수 지연 가능성을 확인한다.
6. 위험에 동의하고 한도·단위 안에서 참여한다.
7. 예치, 중요 변경, 마일스톤 증빙·승인·지급, 쿠폰을 추적한다.
8. 모집 종료 후 회수를 요청하면 신규 투자 예약과 FIFO로 매칭될 때까지 기다린다.

### 소상공인

1. 소상공인 계정으로 로그인한다.
2. 사업자번호, 대표자, 개업일, 영업신고, 주소와 소개를 등록한다.
3. 주소를 분석해 입지 지표를 확인하고 재무·위험 수치를 입력한다.
4. 입력값은 `owner_claimed` 상태의 주장으로만 저장되고 예비점수만 생성된다.
5. POS·카드매출, 부채·월 상환, 납세 확인 자료를 이미지로 올린다.
6. AI가 문서별 OCR 추출 후 식별값, 기간, 매출, 부채, 상환, 납세, 중복, 신뢰도를 순서대로 대조한다.
7. 모든 필수 검사를 통과하면 `ready_for_admin`이 된다.
8. 운영자가 원본 대조 근거를 기록하고 승인해야 `approved`와 공식평가가 된다.
9. 목표금액, 사용계획, 위험대응, 6개 공시, 합계 100% 지급단계를 작성해 모집심사를 요청한다.
10. 공개 후 현재 마일스톤의 계약서·세금계산서·영수증·완료사진을 제출한다.

### 운영자

1. 재무 원자료 검증 대기열에서 AI 단계, 누락, 불일치, 신뢰도를 본다.
2. 원본과 구조화 결과를 대조하고 근거를 기록해 공식 승인 또는 반려한다.
3. 공식평가가 없는 모집은 공개하지 않는다.
4. 예치 확인, 집행 증빙 승인, 단계별 지급을 순서대로 처리한다.
5. 모든 결정은 `audit_events`에 남긴다.

## 5. 재무자료 AI 오케스트레이션

### 신뢰 상태

```text
owner_claimed
  → needs_documents / mismatch
  → ready_for_admin
  → approved 또는 rejected
  → approved에 연결된 credit_assessment만 is_official=true
```

재무 입력을 수정하면 DB 트리거가 검증 연결과 기존 공식평가를 즉시 무효화한다. 모집 제출 RPC는 `is_official=true`인 평가와 `approved` 검증 실행이 같은 `verification_run_id`로 연결돼 있어야 통과한다.

### 순차 검사

1. 형식·용량: PNG/JPG/WebP, 최대 6개, 각 6MB, 합계 20MB
2. 문서 분류: 매출, 부채, 납세, 은행, 기타
3. 사업자 식별값 대조
4. 문서 기준기간 확인
5. 6개월 평균매출 대조
6. 총부채와 월 상환액 대조
7. 납세 상태 대조
8. SHA-256 지문으로 같은 원본 중복 확인
9. OCR 평균 신뢰도와 경고 집계
10. 운영자 검토 가능 여부 결정

오차율 5% 이하는 일치, 5~15%는 확인 필요, 15% 초과는 불일치로 분류한다. AI는 구조화와 검토 준비 여부만 계산하며 공식 승인 권한이 없다.

검증 실행 레코드의 `INSERT` 권한은 브라우저의 `authenticated` 역할에서 회수했다. `/api/ai.js`가 사용자 토큰으로 소상공인 권한을 먼저 확인한 뒤 서버 전용 `SUPABASE_SERVICE_ROLE_KEY`로만 구조화 결과를 저장하므로, 사용자가 REST 호출로 `ready_for_admin` 결과를 직접 만들 수 없다. 이 키는 서버 환경에만 두고 `VITE_` 접두사를 붙이지 않는다.

### OCR 사용 감사

| 구간 | 이전 | 현재 판단 |
|---|---|---|
| 모집 전 재무검증 | 직접 입력만 있고 원자료 OCR 없음 | 핵심 결손이었으며 새 오케스트레이션으로 보완 |
| 모집 후 집행증빙 | 영수증·계약서 이미지를 OCR 분석 후 운영자 승인 | 적절한 사용. 자동 지급 금지 유지 |
| 월 매출 성장 보너스 | 사업자 직접 입력이 즉시 쿠폰 적립률을 올림 | 조작 가능 경로여서 자동 보너스 0으로 차단 |

현재 재무검증은 개인정보 최소화를 위해 DB에 base64 원본을 저장하지 않고 구조화 결과와 SHA-256 지문만 저장한다. 운영자가 같은 원본을 비동기로 열람하려면 Supabase Private Storage, signed URL, 악성파일 검사, 보존·삭제 정책이 추가돼야 한다. 이 연결 전에는 화면에서도 “원본 보관 완료”라고 표시하지 않는다.

## 6. 역할별 Knowledge Graph

### 목적

일반 LLM 프롬프트만으로 “어떻게 투자해?”, “등록하려면 무엇을 업로드해?”에 답하면 구현하지 않은 서류나 절차를 지어낼 수 있다. 따라서 역할별 절차와 실제 저장 상태를 노드·관계·출처로 제한하고, 관련 노드만 AI 컨텍스트에 넣는다.

### 투자자 그래프

```text
투자 시작 → 상품 구조 이해 → 사업·위험 검토 → 감내능력·분산 확인
         → 위험 동의·참여 → 모집·집행 추적 → FIFO 회수 요청

Business ─RAISES→ Campaign ─HAS_MILESTONE→ Milestone
Business ─ASSESSED_BY→ CreditAssessment
Business ─LOCATED_IN→ CommercialArea
InvestorHolding ─INVESTED_IN→ Campaign
```

### 소상공인 그래프

```text
사업체 등록 → 재무 주장 입력 ─REQUIRES→ 근거자료 업로드
근거자료 ─VERIFIED_BY→ AI 교차검증 ─REVIEWED_BY→ 운영자 원본 확인
운영자 확인 ─UNLOCKS→ 모집안·공시 → 모집 공개 → 집행 증빙

Business ─CLAIMS→ FinancialClaim
VerificationRun ─REVIEWED_BY→ AdminReview
Business ─LOCATED_IN→ CommercialArea
Business ─RAISES→ Campaign
```

### 구현

- 프론트 동적 그래프: `src/knowledge-graph.js`
- 영구 정책 그래프: `knowledge_nodes`, `knowledge_edges`
- DB 조회: `role_knowledge_graph(role, business_id)` RPC
- 질의 검색: 질문 토큰과 노드 label/properties를 대조해 최대 14개 노드와 24개 관계만 직렬화
- 절차 질문: 결정적 그래프 응답을 사용해 외부 모델 없이도 정확히 답변
- 일반 질문: 검색된 그래프와 현재 화면 데이터를 LLM에 전달
- 메타데이터: `source_ref`, `verification_status`, `evidence_refs`, `confidence`

초기에는 서비스 원장과 트랜잭션을 함께 다루는 PostgreSQL property graph가 운영·권한·감사에 유리하다. 노드·관계가 수백만 건으로 늘고 다중 홉 추천 성능이 병목일 때 Neo4j 같은 전용 그래프 저장소를 검토한다.

## 7. 입지분석 연결

기존 `commercial_area/` 모듈을 투자자와 소상공인 양쪽에서 사용한다.

- 투자자: 관심 지역·주소 입력 → 상권 카드 → 주소가 맞는 예시/공개 모집 비교
- 소상공인: 사업장 주소 입력 → 상권 분석 → 유동인구 증감, 상권매출 증감, 경쟁밀도, 폐업률 자동 반영
- AI: 현재 사업 또는 모집의 주소를 `CommercialArea` 노드로 연결해 답변 근거에 포함

현재 데이터는 로컬 상권 카탈로그 기반의 결정적 매칭이다. 실제 외부 상권 API를 연결할 때는 좌표, 업종코드, 기준월, 출처, 갱신일을 저장하고 주소 미매칭을 임의 추정하지 않는다.

## 11. 운영 원칙

1. 사업자 입력값은 검증 전까지 주장으로 표시한다.
2. OCR 신뢰도는 진위나 승인과 동일하지 않다.
3. AI는 지급·공식평가·모집공개를 자동 승인하지 않는다.
4. 최소 성립, 취소, 환불, 중요 변경을 참여 전에 명확히 고지한다.
5. 투자자는 집중과 회수 지연 위험을 이해해야 한다.
6. 탐색·랭킹은 객관적 기준과 출처를 공개한다.
7. 결제·예치 파트너와 내부 참여 원장을 분리하고 주기적으로 대사한다.
8. 실제 수치가 없으면 AI가 만들지 않고 자료 부족을 표시한다.
9. 개인정보는 목적에 필요한 최소 범위만 수집하고 원본 접근을 기록한다.
10. 쿠폰형 모델을 대출·지분·확정수익 상품처럼 설명하지 않는다.

## 12. 완료 기준

- 투자자가 “어떤 식으로 투자해?”라고 물으면 투자자 그래프 순서와 현재 상품 위험으로 답한다.
- 소상공인이 “등록하려면 무엇을 업로드해?”라고 물으면 사업체 등록, 주장 입력, 필수 3종 재무자료, 검증, 모집안 순서로 답한다.
- 사업자 입력만으로 `is_official=true` 평가를 만들 수 없다.
- 필수 재무자료 누락·불일치·낮은 신뢰도·중복이면 운영자 승인 버튼과 DB RPC가 모두 막는다.
- 재무 입력 수정 시 기존 공식평가가 무효화된다.
- 공식 재무검증 없이는 모집심사를 요청하거나 공개할 수 없다.
- 수기 월매출은 투자자 혜택을 자동 변경하지 않는다.
- 투자자와 소상공인 모두 주소를 입력해 같은 입지분석 체계를 사용한다.
- 테스트와 프로덕션 빌드가 통과한다.
